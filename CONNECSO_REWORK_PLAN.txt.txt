17. SUBSCRIPTION REFRESH LIFECYCLE
----------------------------------------------------------------------

There are TWO concepts:

A. Persistent server history / preference data
B. Current subscription-cycle availability state

They MUST NOT be treated as the same data.

AUTO REFRESH DEFAULTS:

Active subscription:
    every 6 hours

Inactive/other subscriptions:
    every 12 hours

Auto Refresh should default to ON even if the user never manually enables it.

Each subscription may have:
- autoRefreshEnabled
- configured refresh interval
- lastRefreshAt
- nextRefreshAt

User may customize the interval.

When a subscription becomes Active:

it adopts/effectively uses the Active policy (default 6h).

When it stops being Active:

it returns to the inactive/background policy or its configured background behavior
(default 12h).

Manual Refresh:

If user manually refreshes a subscription, reset/restart that subscription's refresh timer.

IMPORTANT DATA RESET RULE:

Refreshing the subscription must NOT delete:

- Last Good data,
- historical server weight/quality metadata,
- persistent previous-success information,
- country priority.

Refresh SHOULD reset current availability-cycle information such as:

- DEAD status,
- current consecutive failure counter,
- current per-cycle availability state.

The critical rule:

Subscription refresh gives DEAD nodes another chance.

It does NOT wipe the persistent intelligence/history about those nodes.

19. NEW REAL PING METHOD
----------------------------------------------------------------------

The existing ping system is not considered useful enough.

The new primary displayed ping must use a real request through the actual proxy/Xray outbound.

Desired conceptual measurement:

start timer
    ↓
request travels through selected node/Xray outbound
    ↓
TLS/HTTP exchange
    ↓
first valid response byte / response header arrives
    ↓
stop timer

Displayed Ping = Real Delay / First Byte latency

Do NOT use:
- ICMP as the primary displayed value,
- local SOCKS connect time,
- localhost proxy-connect time,
- arbitrary internal socket timing.

Diagnostic values may optionally retain things such as:
- HTTP status,
- proxy connect,
- TLS via outbound,
- First Byte,

but the primary ping used for user display/scoring is First Byte / Real Delay through the
actual outbound.

Use a lightweight stable endpoint suitable for connectivity testing, ideally a 204-style
endpoint, and keep endpoint behavior consistent so server-side processing variance is minimal.

The test MUST actually traverse the node being evaluated.

20. INITIAL SERVER SCORING
----------------------------------------------------------------------

Initial server selection has three primary score components.

A. COUNTRY PRIORITY

Tier/group scores:

50 points:
- Netherlands
- Germany
- United Kingdom

40 points:
- Turkey
- France
- United States

30 points:
- Canada
- Italy

Note:
Turkey is also part of the first connection search Tier even though its Country Score is 40.

Country score is persistent/static configuration, not derived from latency.

B. LAST GOOD

If the node is the previously successful Last Good connection:

+20 points

Last Good must persist across:
- app restart,
- subscription refresh.

Last Good must NOT be reset by the 6-hour active-subscription refresh.

C. RELATIVE REAL PING SCORE

Maximum:
40 points

The best currently measured candidate receives:
40.

Other nodes receive a smooth/proportional score based on how much slower they are relative
to the best current ping.

Do NOT use crude fixed buckets.

Desired behavior concept:

best = 100ms → 40

a server approximately 10% slower:
approximately 10% less Ping Score

a server approximately 20% slower:
approximately 20% less Ping Score

etc.

Use a safe bounded continuous formula.

A reasonable implementation basis can be proportional/ratio based, but verify its behavior
for large differences and do not produce negative values.

The algorithm must still work when the USER'S ENTIRE INTERNET IS BAD.

Example:

A = 300ms
B = 330ms
C = 380ms
D = 450ms

A is still the best current candidate and should receive full/near-full ping preference,
rather than treating every node as uniformly useless.

Initial Final Score concept:

FinalScore =
    CountryPriority
  + RelativePingScore
  + LastGoodBonus

Current maximum theoretical score:
50 + 40 + 20 = 110

The degradation penalty described later is NOT normally part of initial server selection.

21. TIERED INITIAL CONNECTION SEARCH
----------------------------------------------------------------------

Do NOT wait for every server in the subscription before connecting.

Initial search tiers:

TIER 1:
- Netherlands
- Germany
- United Kingdom
- Turkey

TIER 2:
- France
- United States

TIER 3:
- Canada
- Italy

When user presses CONNECT:

1. use cached subscription data;
2. DO NOT refresh subscription simply because Connect was pressed;
3. remove nodes that are DEAD for the current subscription availability cycle;
4. probe Tier 1 candidates first;
5. calculate Real Ping and score viable Tier 1 candidates;
6. if a sufficiently viable Tier 1 candidate exists, select/connect without waiting for
   Tier 2 or Tier 3;
7. expand to Tier 2 only if Tier 1 does not provide a usable candidate;
8. expand to Tier 3 only if required.

Historical data / Last Good can influence probe order inside the tier.

Example:

If Germany is Last Good and part of Tier 1, probing it early is desirable.

Do NOT wait unnecessarily for:
- America,
- Canada,
- Italy,

when healthy high-priority European candidates are already available.

Parallel/concurrency controlled probing may be used.

Do not probe every node strictly sequentially.

Avoid allowing one timeout node to block the whole Connect operation.

Healthy initial connection target UX should be fast.

With normal real delays around ~90–150ms and healthy candidate nodes, target approximate
connection startup on the order of roughly 1–2 seconds rather than waiting for all servers.

----------------------------------------------------------------------
22. NODE RUNTIME STATES
----------------------------------------------------------------------

Use clear state semantics.

At minimum:

UNKNOWN
HEALTHY
DEGRADED
DEAD

UNKNOWN:
not yet sufficiently evaluated in the current subscription availability cycle.

HEALTHY:
responding normally.

DEGRADED:
still responds, but current quality is significantly worse than baseline / peers.

DEAD:
repeated hard failures have demonstrated unavailability for this subscription cycle.

Important:

300ms, 500ms, etc. are NOT automatically DEAD if the node still responds.

Slow response = DEGRADED.

No usable response / timeout / connection failure contributes to HARD FAILURE / DEAD logic.

----------------------------------------------------------------------
23. DEAD NODE POLICY
----------------------------------------------------------------------

Five consecutive hard failures:

FAIL
FAIL
FAIL
FAIL
FAIL

→ mark node DEAD for the CURRENT subscription cycle.

Once DEAD:

- exclude from normal ping loop,
- exclude from initial server selection,
- exclude from failover candidates,
- do not waste repeated probes on it.

It stays DEAD until that subscription is refreshed.

On subscription refresh:

DEAD → UNKNOWN

and the node gets another opportunity.

Example:

Italy is physically/offline for hours.

Cycle A:
5 fails → DEAD → stop probing.

At next subscription refresh:
Italy → UNKNOWN → gets tested again.

If still offline:
another 5 failures → DEAD again.

This is intentional.

DEAD is not permanent historical deletion.

----------------------------------------------------------------------
26. GLOBAL NETWORK DEGRADATION VS NODE-SPECIFIC DEGRADATION
----------------------------------------------------------------------

This distinction is essential.

Do NOT punish the current node simply because its ping became high.

Example — GLOBAL degradation:

DE normally 120 → now 320
NL normally 110 → now 305
UK normally 125 → now 330
TR normally 140 → now 315

This strongly suggests the user's current network/internet condition degraded.

Do NOT apply a node-specific degradation penalty to Germany merely because it is over 300.

Avoid unnecessary server switching.

Example — NODE-SPECIFIC degradation:

DE normally 120 → now 320
NL 110 → 115
UK 125 → 130
TR 140 → 145

Here Germany/path is likely specifically degraded.

Node-specific penalty may apply.

Use comparison against:
- the current node's baseline,
- concurrent health of peer candidates,
- majority/consensus of the other usable nodes.

A practical threshold around 60–70% of other relevant nodes remaining near their own baseline
may be used as a starting point, but design this robustly and document the exact chosen rule.

The point is:

current node degraded
AND
most other nodes stable
→ node-specific degradation

most nodes degraded together
→ probable global network degradation
→ do not penalize/switch aggressively.

----------------------------------------------------------------------
27. DEGRADATION PENALTY
----------------------------------------------------------------------

Degradation affects AUTOSWITCH decisions, not normal initial selection.

The user wants scaled negative scores.

Use the node's baseline rather than only universal fixed latency thresholds.

Illustrative desired behavior when baseline is around 110ms:

normal / reasonable drift:
approximately <=150ms
→ 0 penalty

moderate degradation:
~151–200ms
→ approximately -5

worse:
~201–250ms
→ approximately -10

worse:
~251–299ms
→ approximately -15

severe:
300ms+
→ stronger penalty, e.g. around -25 and increasing if appropriate

very severe but still responding:
may increase further, e.g. -30 / -35 depending on chosen scaling

Hard failure:
do not treat as a giant latency penalty;
it transitions into failure/emergency/dead logic.

IMPORTANT:
These values should behave as a scalable severity model, not a brittle exact-value table.

If baseline is different, adapt relative to that baseline.

The user's intent:

- degradation should reduce current node preference progressively,
- 5-point steps are suitable in moderate ranges,
- once the node reaches ~300ms relative to a normal ~110 baseline, a larger penalty is justified,
- but penalty applies only when peers show this is node-specific rather than a global network problem.

28. EVENT-DRIVEN CONNECTION HEALTH MONITOR
----------------------------------------------------------------------

Do NOT implement AutoSwitcher as an infinite busy polling analysis loop.

Use an event-driven architecture.

Conceptually:

----------------------------------------------------------------------
29. HARD FAILURE DEFINITION
----------------------------------------------------------------------

Hard Failure is NOT "ping is high".

Examples of valid Hard Failure signals for CURRENT NODE:

- real outbound probe times out,
- no usable HTTP response before configured timeout,
- actual outbound connection fails,
- TLS/transport cannot establish through current node,
- Xray/core reports meaningful current outbound/session failure,
- route is present locally but actual outbound connectivity is unusable.

Examples that are NOT Hard Failure:

300ms response
500ms response
slow but valid HTTP response

Those are degraded, not dead.

A single hard failure should trigger emergency verification rather than waiting for the next
normal one-minute or ten-minute monitoring pulse.

----------------------------------------------------------------------
30. EMERGENCY VERIFICATION
----------------------------------------------------------------------

Normal monitoring intervals are too slow for connection failure recovery.

When a current-node Hard Failure occurs:

DO NOT wait:
- 1 minute,
- 10 minutes,
- next scheduled monitoring pulse.

Start a fast emergency verification sequence.

Conceptual behavior:

t = 0:
normal/current probe hard-fails

→ enter emergency verification

retry current node at short interval,
approximately 2–3 seconds apart.

A reasonable target:

initial hard failure
+ two fast confirmation retries

Three consecutive fast hard failures total
→ allow immediate Emergency AutoSwitch

Example:

t=0s    FAIL
t≈2s    FAIL
t≈4s    FAIL
→ switch

This should normally detect a fully broken current route within only a few seconds.

Do not confuse this with DEAD state.

3 fast failures:
→ switch away from current server

5 consecutive total hard failures:
→ DEAD

The node may therefore be switched away from before it is permanently excluded for the
current subscription cycle.

----------------------------------------------------------------------
31. AUTOSWITCHER
----------------------------------------------------------------------

AutoSwitcher is separate from the DEAD-state system.

A node may be bad enough to leave but not yet DEAD.

AutoSwitcher must handle:

A. HARD FAILURE SWITCH
B. NODE-SPECIFIC DEGRADATION SWITCH

Do NOT switch because another server wins by 1–2 points for one moment.

Do NOT create ping-pong switching.

For degradation switch:

- confirm current node degradation,
- verify peers are not globally degraded,
- recalculate current score including degradation penalty,
- identify a genuinely better candidate,
- require meaningful score advantage,
- ideally require confirmation across more than one relevant observation unless severity
  makes immediate action necessary.

A score margin around 10–15 points is a reasonable starting range, but inspect actual score
distribution and choose/document the final threshold.

Remember scoring ranges:

Country:
30 / 40 / 50

Ping:
0..40

Last Good:
+20

Degradation:
negative when applicable

Example concept:

Current DE:
Country 50
LastGood 20
Current Ping score low
Degradation -25

Candidate NL:
Country 50
Ping score high
No degradation

If NL is clearly superior → switch.

----------------------------------------------------------------------
32. AUTOSWITCH COOLDOWN
----------------------------------------------------------------------

After a normal degradation-based AutoSwitch, use a cooldown to avoid oscillation/ping-pong.

During cooldown:
minor normal quality differences should not immediately switch again.

Hard Failure must be allowed to override cooldown.

A starting value around 3–5 minutes is reasonable.

Choose/document an exact implementation based on existing timing architecture.

Do NOT allow the app to bounce:

DE → NL → DE → NL

because of small transient differences.

After switching away from a degraded server:
continue monitoring that old server according to normal eligibility rules unless it becomes DEAD.

If it later recovers:
do not immediately switch back merely because it is historically preferred.

Current healthy connection stability matters.

----------------------------------------------------------------------
33. LAST GOOD
----------------------------------------------------------------------

Last Good bonus:

+20

Last Good represents a previously successful, good-quality connection.

It must persist across:
- process restart,
- app restart,
- subscription refresh.

But Last Good is only a preference, not absolute authority.

A node with terrible current quality must not win solely because it is Last Good.

This is why Last Good is 20 rather than the previously considered 35.
